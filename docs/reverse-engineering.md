# Reverse engineering guide

The aim is **behavioural accuracy, not a matching decompilation**. We study
`hover.exe` in Ghidra, understand what each part does, and then write clean,
portable C in `src/engine/` that does the same thing. Decompiler output is a
reference only. Never paste it into the repo.

## Setup

1. Install [Ghidra](https://github.com/NationalSecurityAgency/ghidra/releases) 11+ (Java 21).
2. Get `hover.exe` from your own copy of the game. Compare
   `sha256sum hover.exe` with [hashes.txt](hashes.txt): addresses in this repo
   refer to that build.
3. Build the local project. This also applies every shared symbol:

   ```bash
   export GHIDRA_HOME=/path/to/ghidra
   re/setup.sh /path/to/hover.exe
   ```

   This creates `re/ghidra_proj/` (open it in the Ghidra GUI) and
   `re/out/hover_decomp.c`, a full decompile. Both are gitignored.

4. To decompile specific functions from the command line:

   ```bash
   re/decomp.sh 412980 411b10
   ```

## Sharing what you learn: `re/symbols.csv`

Ghidra project files don't merge well, so names are shared as text instead.
When you identify a function or global, add a line:

```
address,kind,name
00412980,func,CMerlinTexture::Serialize
00461cfc,data,g_textureSkipMips
```

`kind` is `func` or `data`. `A::b` places `b` in namespace `A`. In the Ghidra
GUI, run **Script Manager → VitaHover → ApplySymbols** to pull in other
people's names. Keep the file sorted by address so diffs stay readable.

The first 119 entries were generated by `re/scripts/find_runtime_classes.py`,
which finds every MFC `CRuntimeClass` record.

## Map of hover.exe

- PE32, i386, MSVC (1995). Statically linked MFC 3.x and the C runtime.
- `.text` 0x401000–0x45f56e. **Game/engine code is roughly 0x401000–0x430000**.
  Everything above that is mostly MFC and CRT, so skip it.
- No DirectX or WinG: rendering is pure software into a DIB, then GDI blits it.
- Audio is waveOut (custom mixer) plus `midiStream*`. Timing is `timeSetEvent`.
  Input is the keyboard (configurable) and `joyGetPos`.
- Debug strings name the original source files (e.g. `CTexture.h`,
  `MAXTEXTURESIZE`) and are useful anchors.

### Tips

- MFC vtable layout: `[0] GetRuntimeClass, [1] destructor, [2] Serialize, ...`.
  A runtime class's `CreateObject` gets you the constructor, the constructor
  gets you the vtable, and slot 2 of the vtable is the file format.
- The inlined `CArchive` reads look like
  `if (ar->m_lpBufMax < ar->m_lpBufCur + N) FillBuffer(...)`. Offsets `+0x1c` and
  `+0x20` are `m_lpBufCur` and `m_lpBufMax`. `FUN_00452a1e` is `CArchive::Read`.
- Global `DAT_00461d00` is a bump allocator for the texture heap.

## Checking your work

Tools in `tools/` prototype a format in Python first. Once it's understood,
port it to C in `src/engine/` with a test in `tests/` that runs against the
real files.
